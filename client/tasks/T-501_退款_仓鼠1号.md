## 0. 为什么这个排第一

结账**前**的退菜 T-303 已经能做（`OrderEntryViewModel.TryRefundLine`）。

但结账**后**——客人已经付了钱，说要退单、退菜、或者整单作废——**现在没有完整流程**。

```
现状：
  待结账订单退菜  ✅ T-303 已实现
  已结账订单退菜  ❌ 没有流程
  整单退款        ❌ 没有流程
  冲正（收付双方都取消）❌ 没有流程
```

**这是收银员每天都会碰的操作**，优先级高于所有新功能。

## 2. 三种操作的区别（**别混在一起**）

```
退菜Refund Item    只退其中几个菜，钱退一部分
                    菜可能已经做了 → 要通知后厨撤单
整单退单 Refund Order   整单退，已付的钱全退
冲正   Void/Cancel 订单作废，不产生退款
                    （用于录错单、测试单）
```

**收银员最容易搞混的就是这三个。UI 上必须一眼分清。**

## 3. 功能要求

### 3.1 退菜（部分退）

```
订单 A08已结账 ¥128
  ├─ 退牛肉面 ¥18（客人不要了）
  ├─ 退饮料 ¥8
  └─ 实退 ¥26
```

**要求**：
- 可**多选**明细行，一次退多个
- 已做菜的退菜要**联动后厨撤单**（`Hardware/Printers`，T-106 的打印能力）
- 退菜必须**填原因**（复用 `RefundReasonViewModel`）
- 退菜后**订单不能变成已退单**，而是「部分退款」
- 打印**退菜单**（厨房要看到撤单）

**关键约束**：
```
已打印的退菜单要能重复打印（厨房漏单了要补）
```

### 3.2 整单退单

```
订单 A08 已结账 ¥128，实收现金 ¥128
  ├─ 退单：¥128
  ├─ 原路退回现金：¥128，钱箱 +128
  └─ 订单状态 → Refunded
```

**要求**：
- 退单前**二次确认**，显示「将退回 ¥128，确认退单？」
- 支持**部分退款**（128 退了 100，剩 28 是抹零或投诉补偿）
- **多次退单**要能累加，不能超过实收金额
- 退单后打印**退款单**
- 退单必须**记录操作人和时间**

**⚠️ 金额红线（必须测）**：
```
累计退款金额 > 实收金额 → 必须拒绝并报错
多次退款累计超实收       → 必须拒绝
退款为负/零             → 必须拒绝
```

### 3.3 冲正（作废）

```
录错单了 / 压测试单 / 客人取消了没点
  → 作废，不退钱（本来就没收）
```

**要求**：
- 作废**只对未结账订单**有效
- 已结账订单不能作废，只能退单
- 作废要**填原因**
- 作废后**桌台要释放**（A08 变回空闲）← **这条最容易漏**
- 作废单在订单管理里要**灰显但可见**（财务要能查到）

### 3.4 权限

```
店长     可退单、可冲正、可看全部
收银员   可退菜、可部分退款
         整单退单需店长授权（金额超阈值时）
```

**要求**：
- 整单退单**金额超阈值必须店长确认**（如 > ¥200）
- 阈值可配置
- 授权要**记录**（谁授权的、什么时候）

### 3.5 交班联动

```
本班已结账 ¥8600
  退菜 3 笔 ¥88
  退单 1 笔 ¥56
  → 本班净额 ¥8456
```

**要求**：
- 退菜/退单要**计入当前班次**（不是原班次）
- T-309 的 `ShiftCalculator` 必须能正确处理退款
- 报表（T-310）的营业额要减掉退款 ← **它已经实现了，确认对接正确**

## 4. 计算逻辑（**必须精确**）

```csharp
public class RefundCalculator
{
    // 可退金额 = 实收 - 已退累计
    decimal CalcRefundable(Order order);
    
    // 退菜金额校验：不能超过该行金额
    bool ValidateItemRefund(OrderItem item, decimal amount);
    
    // 整单退款校验
    bool ValidateOrderRefund(Order order, decimal amount, out string? reason);
    
    // 退款后订单状态：全退 → Refunded，部分退 → 仍 Settled
    OrderStatus CalcStatusAfterRefund(Order order, decimal totalRefund);
    
    // 退款计入当前班次，不计入原班次
    long ResolveShiftId(Order order, long currentShiftId);
}
```

**必须覆盖的边界**：

| 场景 | 期望 |
|---|---|
| 退款 > 实收 | 拒绝 |
| 多次退款累计 > 实收 | 拒绝 |
| 退款 = 0 | 拒绝 |
| 退款 < 0 | 拒绝 |
| 退菜金额 > 该行金额 | 拒绝 |
| 已全退后再退 | 拒绝 |
| 整单退完后又退菜 | 拒绝 |
| 退款浮点精度 | 用 decimal，禁 float |
| 退菜后结账金额重算 | 正确 |

**取整**：显式 `MidpointRounding.AwayFromZero`。

## 5. ⚠️ Domain 缺口（**不要自己改**）

`Order` 已有 `AmountRefund`、`OrderStatus.Refunded`、`OrderItem.IsRefunded`。

**缺的**：

| 缺口 | 用途 |
|---|---|
| 退款明细实体 | 每次退款的记录：退哪单、退哪行、退多少、原因、操作人、时间 |
| `IRefundRepository` | 退款仓储 |
| `RefundType` 枚举 | 退菜 / 整单退 / 冲正 |
| 订单的 `PartiallyRefunded` 状态 | 部分退款和全退要能区分 |

**处理方式**：**不要改 Domain**（冻结），在报告里列「Domain 缺口清单」。

**同时**：把计算逻辑做成纯类（`RefundCalculator`），先用假数据测；仓储用**可注入接口 + 假实现**。

## 6. UI 工艺要求

必读 `client/tasks/T-005_控件库_仓鼠3号.md` 第 3 节。

**Craft Read**：`CRAFT_LEVEL` 7 / `MOTION_INTENSITY` 2 / `VISUAL_DENSITY` 6 / `DESIGN_VARIANCE` 3

**关键要求**：

- **三个操作必须在UI 上明确区分**，不能让收银员误触
  - 退菜：蓝色系
  - 退单：橙色系
  - 冲正：红色系（破坏性最强）
- **金额确认要显眼**：退单弹窗要显示「大字 ¥128 退回」
- **退菜选择要直观**：明细行左侧 checkbox，选中行高亮
- **必须显示已退金额**，让收银员知道还能退多少
- 退单确认弹窗要显示**具体影响**（退多少、订单变什么状态、桌台会不会变），不是「确定吗」
- **权限不足时按钮置灰+ 说明原因**，不要点了才报错
- 已退款的部分要在明细行上**标灰/加标记**，不要完全隐藏
- empty / loading / error / conflict 四态
- 退款提交失败的错误要**说清楚**（如「累计退款 ¥156 超过实收 ¥128」）
