## 3. 功能要求

### 3.1 加菜

```
点商品 → 弹出规格选择（如果有规格）→ 确认 → 加到明细
```

- 无规格商品：点了直接加
- 有规格：先选规格（茶饮：大小/温度/糖度/加料）
- 称重商品：点了**不能立刻确定金额**，走称重流程（见 3.4）
- 沽清商品：置灰不可点（或点了提示「已沽清」）

**重复点击同款**：数量 +1（不弹规格选择，除非该商品有可变规格）
**长按/连点**：进入规格选择（允许同款不同规格）

### 3.2 改数量与价格

| 操作 | 权限 | 说明 |
|---|---|---|
| 改数量 | 服务员+ | 用 `QtyStepper` |
| 改单价 | **仅店长** | 权限检查，敏感操作要记日志 |
| 改整单折扣 | **仅店长** | 同上 |
| 赠菜 | **仅店长** | 数量保留但金额归零，要明显标记 |

**要求**：
- 改价/折扣弹出时**必须显示原值**，且要二次确认
- 赠菜行要有**视觉标记**（删除线或「赠」标签），不能只靠金额 0 区分（真 0 元商品也存在）

### 3.3 备注与做法要求

```
宫保鸡丁
  └─ 做法：微辣 / 中辣 / 特辣 / 不辣
  └─ 备注：不要葱
```

- 做法来自商品预设的规格（可留空）
- 备注自由输入（最多 30 字）
- 备注会打进后厨单（`T-107` 已实现后厨单模板）

### 3.4 称重商品

```
点「海鲜（称重）」→ 提示「请输入重量」→ 用 NumberPad 输入（kg）
  → 金额 = 重量 × 单价（保留 2 位，四舍五入）
```

**要求**：
- 重量输入要有**单位标识**（kg）
- 可以调电子秤读数（`Hardware/Scales` 已有），但**手输必须可用**（秤坏了不能没法点单）
- 已有的电子秤重量接入 → 读数自动填入
- 称重商品金额**不是用户直接填的**，是算出来的

### 3.5 挂单 / 取单

```
挂单：把这桌的临时单存起来（客人先看看、等会儿再点）
取单：从挂单列表恢复到某桌
```

- 挂单列表显示：桌号/人数/时间/金额/明细数量
- 挂单和正式订单**数据上要区分开**，结账时只认正式订单
- 超过 30 分钟的挂单提示「可能已遗忘」
- 挂单不能被并台/换台影响

### 3.6 退菜 / 作废

```
选中明细行 → 退菜 → 确认
```

- 已下单的菜要退，需要**权限**（店长或服务员，视设置）
- 退菜要**记录原因**（不要了/上错了/客人不要了）
- 退菜后要能打印「退菜单」给厨房
- 结账后不能退菜（要到订单管理模块处理）

### 3.7 提交下单

```
点「提交下单」
  → 生成订单（状态：已下单/待结账）
  → 写 outbox 队列
  → 打印后厨单（按档口分）
  → 提示「已下单」并回到桌台页（可继续开台）
```

**要求**：
- 提交要**防重复**（连点两下不能出两单）—— 用 `clientOrderNo` 幂等键（数据层已支持）
- 提交失败要能重试，且重试不产生重复订单
- 提交后可选：继续点单 / 清台 / 换台

## 4. 金额计算（**核心逻辑，必须精确**）

**这是整个 POS 最容易出错的地方。** 单独抽出纯逻辑类，重点测。

```csharp
public class OrderCalculator
{
    // 行金额
    decimal CalcLineAmount(OrderLine line);          // 数量 × 单价 - 行折扣

    // 整单
    decimal CalcOrderTotal(IReadOnlyList<OrderLine> lines, decimal discount);
    decimal CalcPayable(decimal total, decimal discount);
    decimal CalcChange(decimal received, decimal payable);
}
```

**必须处理的情况**：

| 情况 | 规则 |
|---|---|
| 称重商品 | 重量 × 单价，保留 2 位 |
| 行折扣 | 先算行金额再打折 |
| 整单折扣 | 打折后可能出现分为单位的尾数，**必须说明取整规则**（四舍五入 / 抹零 / 分为单位） |
| 抹零 | 常见：直接抹掉分（¥128.57 → ¥128.50），**要有开关** |
| 赠菜 | 金额 0，但计入原价合计（对账要用） |
| 退菜 | 从合计里减去 |

**取整规则**：用 `MidpointRounding.AwayFromZero`（收银不是银行家舍入）。**这个要在代码里显式写出来**，不要依赖默认值。

## 5. UI 工艺要求（硬性）

必读 `client/tasks/T-005_控件库_仓鼠3号.md` 第 3 节。

**Craft Read 参考**：
- `CRAFT_LEVEL` 8 / `MOTION_INTENSITY` 2 / `VISUAL_DENSITY` 9 / `DESIGN_DENSITY` 9 / `DESIGN_VARIANCE` 3
- 这是**整个系统信息密度最高的界面**，但密度靠布局不靠缩字号

**关键要求**：
- **明细行的金额要能快速扫读** → 用 `AmountDisplay`（tabular-nums），右对齐，列宽固定
- 商品卡片区要能**滚动流畅**（几十个商品）→ 考虑虚拟化列表
- 购物车（明细区）也要能快速定位到某一行 → 提供「合计」吸底但明细可滚
- 规格选择弹窗要**触控友好**：大按钮、多选项点选后自动收起（不强制点确定，减少点击）
- 提交下单按钮要**足够大且位置固定**（收银员高频操作）
- 防重复提交：按钮要有明确的「处理中」状态
- loading / empty / error / conflict 四态都要有
- conflict = 提交冲突（如订单已被别人结账），要给明确提示和恢复路径

**签名动作建议**：
**桌台头显示「已开 25 分」+ 该桌的历史消费提醒**（老客人来了能认出），这是收银员真正用得上的信息。
