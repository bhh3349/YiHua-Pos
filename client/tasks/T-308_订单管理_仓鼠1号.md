## 2. 业务背景

**收银员最容易犯的错**，全靠这个模块补救：

| 情况 | 处理 |
|---|---|
| **上错菜** | 退菜（整道/部分） |
| **算错了** | 反结账（取消这笔，重新结） |
| **桌台没清** | 重打后厨单（厨房漏做了） |
| **客人要发票/凭证** | 重打小票 |
| **找错零了** | 冲正（记录正负两笔） |
| **订单找不到了** | 搜索（按时间/桌号/金额/订单号） |

**收银员心理**：宁可重打一张单，也不能让客人等。

## 4. 订单详情与操作

### 4.1 详情

```
订单 A20261012001 · A08 · 4人 · 12:28 开台 · 12:45 结账
收银员：张三    班次：午市

明细
  牛肉面 大杯 少冰      ×2    ¥36.00   [已退]
  宫保鸡丁 微辣         ×1    ¥38.00
  珍珠奶茶 大杯         ×3    ¥36.00

原价 ¥110.00  折扣 -11.00  应收 ¥99.00
现金 ¥100  找零 ¥1.00
```

### 4.2 退菜

```
选中明细行 → 退菜 → 选原因 → 确认
```

**要求**：
- 支持**整道退**和**部分退**（退 2 份里的 1 份）
- 退菜数量不能超过已点数量
- 必填原因（不要了 / 上错了 / 客人不要了 / 质量问题 / 其他）
- **退了有正价（未结账时退）** vs **退了已付（结账后退）** 两种路径：
  - 未结账退 → 直接改明细，重算应收
  - **已结账退 → 生成退菜单，不改原单**（原单要保留完整，这是财务凭证）
- 退菜要打印**退菜单**给厨房（`T-107` 后厨单模板）
- 权限：服务员可退（≤N 元）/ 超过金额或已结账的退菜**仅店长**

### 4.3 反结账（取消这笔）

```
已结账订单 → 反结账 → 原因 → 确认
```

- **不删除原单**，而是**生成一张负数单**（冲正）
- 原单状态改为「已冲正」
- 财务上原单和冲正单都在流水里，可追溯
- **仅店长**
- 反结账后桌台恢复占用状态（客人可能还在吃）

### 4.4 重打

```
订单 → 重打 → 选类型（小票/后厨单/交班单）→ 打印
```

- 重打**不改变订单状态**
- 要记录「谁在什么时候重打了」（对账时可查）
- 打印失败给重试入口

### 4.5 跳单（挂起等待）

```
订单 → 跳单 → 记原因 → 订单退出待结队列
```

- 客人说「先不算这桌」，先跳过
- 要能从跳单列表找到并恢复

## 5. 状态机

订单状态流转要明确，**用枚举 + 显式转换方法**：

```
待结 ──结账──> 已结 ──反结账──> 已冲正
  │                │
  │                └──退菜──> 已结(部分退)   ← 注意：已结也能部分退
  │                │
  └──跳单──> 已跳单 ──恢复──> 待结
```

**必须测试的非法转换**：
- 已冲正订单再结账 → 拒绝
- 已冲正订单再退菜 → 拒绝
- 待结订单退菜（应该是允许的，改明细）→ 注意区分
- 已冲正订单重打 → 允许（补打凭证）
- 退菜数量 > 已点数量 → 拒绝
- 已结账订单改数量（不是退菜）→ 拒绝

## 6. UI 工艺要求（硬性）

必读 `client/tasks/T-005_控件库_仓鼠3号.md` 第 3 节。

**Craft Read 参考**：
- `CRAFT_LEVEL` 8 / `MOTION_INTENSITY` 2 / `VISUAL_DENSITY` 8 / `DESIGN_VARIANCE` 3
- 订单管理是「查账」界面，信息密度高，但**可读性优先**

**关键要求**：
- 金额右对齐 tabular-nums（用 `AmountDisplay`），这样**能上下扫读比大小**
- 已退/已冲正的订单要**视觉区分**（但不要用刺眼红色一片——用次级文字 + 状态标签）
- 破坏性操作（反结账、退整道菜）**必须二次确认**，且确认弹窗要显示**具体影响**（不是「确定吗？」，而是「反结账后订单 A2026... 将标记为已冲正，金额 -128.00」）
- 已结账订单的操作按钮要**明显区别于待结订单**（防止误操作）
- empty 状态：搜索无结果 → 给「清除筛选」，不是「暂无数据」
- loading / error / conflict 必做
- 列表滚动流畅（虚拟化）
