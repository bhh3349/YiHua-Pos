## 0. 为什么这个要做

**正餐服务员的核心动作之一就是挂单**，现在完全没有：

```
场景：客人坐下点完单说要「等朋友」，服务员不能干站着
  → 挂单（Park），客人去别桌聊天/接电话
  → 客人回来，服务员要快速找到这张单 → 取单（Recall）
```

```
场景：点完单客人要先结账再开下一桌（凑单/换桌）
  → 预结账（PreSettle）→ 拆单开台
```

**现在这两个都是空白，服务员只能硬扛着。**

## 2. 挂单业务规则

```
挂单（Park）
  - 把桌台当前订单存起来，桌台变「空闲」但保留单
  - 记录：桌号、客人数量、挂单时间、挂单人

取单（Recall）
  - 按桌号 / 客人数量 / 挂单时间找到原单，恢复到桌台

关键约束：
  ① 挂单后桌台必须能再开新单（客人都坐下了）
     → 所以「桌台空闲」和「有挂单」是两个独立状态
  ② 取单后要能继续加菜
  ③ 挂单有时间限制吗？—— 要，超过N 小时提示清理（可配置）
```

**⚠️ 这条最容易做错**：
```
如果你把桌台状态直接改成 Free，挂单信息就丢了。
必须：桌台空闲 + 挂单列表里有记录  ← 两个状态独立
```

## 3. 功能要求

### 3.1 挂单

```
点「挂单」→ 弹窗确认 → 挂单成功
```

**要求**：
- 挂单前要**提示**（客人还在，要确认）
- 挂单后**桌台立即可开新单**
- 挂单列表要能看到：**桌号、客人数、金额、挂单时间、挂单人**
- 挂单要**打印**（厨房要知道这张单挂着）
- 支持**备注**（如「等朋友」「要发票」）

### 3.2 挂单列表（取单入口）

```
┌────────────────────────────────┐
│ A08  4人  ¥128  14:32  张三  等朋友 │
│ B02  2人  ¥56   14:35  李四  打包│
└────────────────────────────────┘
```

**要求**：
- 按挂单时间倒序
- 显示**等待时长**（超过阈值变色提示）
- 快捷搜索：按桌号 / 客人数 / 收银员
- **单击取单**，双击看详情

### 3.3 取单

```
点某条挂单 → 恢复订单到该桌 → 可继续加菜
```

**要求**：
- 取单时**原桌号为空闲时**才能恢复；被占了要**提示并允许换桌**
- 取单后**订单状态恢复 Pending**，可继续点单
- 取单后可以**立即结账**

### 3.4 预结账 / 拆单

```
场景：4人点了 ¥480，其中 2 人先走要先结账
  → 预结账：拆出 ¥240 结掉，剩下的挂单继续
```

**要求**：
- 预结账要能**选拆哪几个菜**（不是简单对半）
- 拆出来的部分**立即结账**，剩下部分保留在原单
- 预结账后**订单可能变成 Pending**（还有未结的菜）
- **桌台状态要跟着变**：部分结清不等于整单完成
- 要能**多次预结账**（分3 桌人分批结）

**⚠️ 边界**：
```
全部菜都结完了 → 订单才变成 Settled
预结账后剩 0 元 → 订单应直接 Settled
剩负数 → 必须拒绝
```

### 3.5 清理机制

```
挂单挂了一晚上没人来
```

**要求**：
- 挂单超过**可配置时长**（默认 4 小时）显示为「超时」
- 提供**批量清理**（老板说"昨天的都清了"）
- 清理前**二次确认**，要显示清理了几单、多少钱

## 4. 计算逻辑（**必须精确**）

```csharp
public class HangOrderCalculator
{
    // 拆单后各部分金额校验
    bool ValidateSplit(Order order, IReadOnlyList<long> itemIds, out string? reason);
    
    // 拆单后订单状态：全结 → Settled，部分结 → Pending
    OrderStatus CalcStatusAfterSplit(Order order, decimal splitAmount);
    
    // 挂单超时判定
    bool IsTimedOut(HangOrderRecord record, TimeSpan timeout);
    
    // 取单时桌台冲突检查
    bool CanRecall(HangOrderRecord record, long deskId, out string? reason);
}
```

**必须覆盖的边界**：

| 场景 | 期望 |
|---|---|
| 拆单选空 | 拒绝 |
| 拆单金额 > 订单总额 | 拒绝 |
| 拆完全部 → 订单 Settled | 正确 |
| 拆单后剩 0 元 | Settled |
| 拆单后剩负数 | 拒绝 |
| 拆单后桌台状态 | 正确 |
| 取单时桌台被占 | 提示并允许换桌 |
| 挂单超时判定 | 边界（刚好N 小时） |
| 多次预结账 | 累加正确 |
| 金额浮点 | 用 decimal，禁 float |

**取整**：显式 `MidpointRounding.AwayFromZero`。

## 5. ⚠️ Domain 缺口（**不要自己改**）

**缺的**：

| 缺口 | 用途 |
|---|---|
| `HangOrder` 实体 | 挂单记录：原订单、桌号、客人数、挂单时间、挂单人、备注 |
| `IHangOrderRepository` | 挂单仓储 |
| `ParkedOrder` 状态枚举 | 订单状态（Pending/Settled 之外需要「已挂起」） |
| 拆单相关字段 | 原单与拆出单的关联 |

**处理方式**：**不要改 Domain**（冻结），在报告里列「Domain 缺口清单」。

**同时**：把计算逻辑做成纯类（`HangOrderCalculator`），先用假数据测；仓储用**可注入接口 + 假实现**。

## 6. UI 工艺要求

必读 `client/tasks/T-005_控件库_仓鼠3号.md` 第 3 节。

**Craft Read**：`CRAFT_LEVEL` 7 / `MOTION_INTENSITY` 3 / `VISUAL_DENSITY` 6 / `DESIGN_VARIANCE` 3`

**关键要求**：

- **挂单列表要快**：服务员取单是高频动作，手指能点到
- **超时挂单要变色**（但不要刺眼，用警告色背景）
- 桌号要**大而醒目**（服务员扫一眼就要找到）
- 拆单界面：明细行要**能多选**，选中高亮，实时显示「拆出 ¥XXX，剩余 ¥YYY」
- **拆出金额要实时更新**，收银员要边选边看
- 预结账按钮和「结账」要**视觉区分**（预结账是部分，结账是全）
- 清理挂单要有**批量确认**，显示总金额
- empty 态要有设计（不是「暂无挂单」，要引导下一步动作）
- loading / error / conflict 四态
- 挂单成功后要有**明确反馈**（返回列表 + 提示），不能让服务员不知道成没成
