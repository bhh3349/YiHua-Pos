> **交付对象**：UI 设计师
> **基准产品**：美团收银智能版
> **文档版本**：v1.0 · 2026-10-13

---

## 一、一句话说明

一套给**中小餐饮门店**（单店，30–200 平米）用的收银系统，
卖 299 元买断装在商家自己的收银台电脑上。

**不是**给大连锁用的企业级系统。

---

## 二、为什么要对标美团收银智能版

商家已经在用美团收银了。让他们换到我们，**迁移成本必须接近零**：

```
学习成本  收银员不用重新学
操作习惯  手指的位置、点击的顺序都一样
心理预期  看到就懂，不用说明书
```

所以**不是「参考风格」，是「对标操作逻辑」**。

请实际体验美团收银智能版，**逐屏对比**下面的功能清单。

## 三、用户和使用环境（**这条最重要，决定所有设计取舍**）

### 3.1 收银员

```
站着操作，一只手可能拿着盘子和筷子
手指可能有油、有水
忙的时候要同时跟客人说话、接钱、找零
单据已经打印出来了，客人就在旁边等着
```

### 3.2 老板

```
不天天用，一周可能看两三次
可能是五十多岁，不熟悉智能手机
看报表要能一眼看懂，不要数字游戏
最关心：今天营业额多少、哪个菜卖得好、损耗大不大
```

### 3.3 硬件环境

```
屏幕：1366×768 到 1920×1080，横屏
输入：鼠标 + 键盘 + 扫码枪（扫码枪 = 键盘输入 + 回车）
可能：触摸屏（但鼠标是主要方式）
可能：小票打印机、钱箱、客显屏、电子秤
```

> ⚠️ **必须适配 1366×768**。这是收银机的主流分辨率，不是 1080P。
> 信息太多放不下是最常见的问题。

### 3.4 使用时长

```
每天：10–14 小时（中午忙 2 小时）
单次操作：3–8 秒完成一个动作
错误成本极高：收错钱、输错桌号、少算一道菜
```

## 五、**特别强调：诊断报告**

这个功能是我们的**核心差异化**，不是普通的「关于」页面。

### 5.1 为什么做

我们卖 299 买断，**没有上门服务**。商家遇到问题只能发微信。

如果每次都要问「你什么版本、什么打印机、报什么错」，
**一次售后要半小时，商家会崩溃。**

### 5.2 设计要求

```
一个按钮 → 导出一份文件 → 商家微信发给我们 → 我们看懂问题

所以：
✅ 一键生成，商家不用做任何选择
✅ 内容要足够定位问题（版本、系统、打印机、网络、最近错误）
✅ 商家看得懂文件名（"逸华-诊断-20261013-下午茶店.txt"）
❌ 不要让商家选要包含哪些内容
❌ 不要分步骤
❌ 不要有"高级选项"折叠面板
```

## 六、视觉方向

### 6.1 基准

**对标美团收银智能版的视觉**，不要自创风格。

### 6.2 我们的品牌色

```
主色：#2F6BFF（蓝）
```

可以调整明度和饱和度，但**色相保持蓝色系**，这是品牌识别。

### 6.3 设计原则（**面向收银台，不是面向消费级 App**）

| 原则 | 具体要求 | 为什么 |
|---|---|---|
| **密度高** | 一屏能看全，不用滚来滚去 | 收银台每秒都在花钱，减少切换=省钱 |
| **点击目标大** | 主要按钮 ≥ 44px 高 | 可能用触控，可能手上有油 |
| **数字要好读** | 金额用等宽数字，右侧对齐 | 收银员要能快速比对大小 |
| **状态一眼分清** | 空/加载/错误/离线各有明确视觉 | 出问题时不能猜 |
| **少动画** | 只保留必要的状态反馈 | 收银台不能等动画 |
| **不用图标代替文字** | 关键操作必须有文字 | 老板年纪大，新员工上手快 |

### 6.4 ⚠️ **明确不要**

```
❌ 大片留白的"现代简约"风      收银台需要的是效率不是呼吸感
❌ 渐变背景 / 玻璃拟态         太花，弱化信息层级
❌ 圆角过大（>12px）           显得像玩具，不像收银机
❌ 阴影太重                    界面本身已经够密了
❌ 英文菜单 / 中英混排         商家是中国老板
❌ 卡通插画 / emoji 图标       不专业
❌ 顶部大标题 + 大副标题        占地方，收银员不看
```

## 七、每个界面的八种状态（**必须全覆盖**）

每个界面都要考虑这 8 种情况，不能只画正常情况：

```
1. 正常      有数据，正常显示
2. 加载中    正在取数据
3. 空        没数据（新店第一天，商品是空的）
4. 错误      出错了，要说清怎么办
5. 成功      操作完成
6. 部分      部分成功（比如 3 张单 2 张成功）
7. 冲突      重复操作（重复点了提交）
8. 离线      网络断了
```

> **「新店第一天所有界面都是空的」这个场景必须设计。**
> 商家装好系统的第一眼看到的就是空状态。

## 八、交付要求

### 8.1 需要交付

```
□ 主界面（点单页）的完整设计稿 —— 高保真，多个状态
□ 全部 87 个界面 / 弹窗的线框图 + 关键页面高保真
□ 设计规范文档：
   - 颜色（完整色板，含语义色）
   - 字体（字号、字重、行高）
   - 间距（8 点或 4 点栅格）
   - 圆角（按层级区分，不要全一样）
   - 阴影（分层，不是单层）
   - 组件库（按钮/输入框/表格/弹窗/标签/卡片/Toast）
□ 图标集（线性，不用面性）
□ 状态说明（哪些状态已画，哪些没画）
```

### 8.2 技术约束（**请务必了解**）

```
技术栈：.NET + Avalonia 11（跨平台，Windows 和 Linux 都要跑）

⚠️ Avalonia 不是 Chrome，用的不是 HTML/CSS
⚠️ 不能用 CSS 变量、Flexbox 以外的现代布局工具
⚠️ 设计稿给结构和规范即可，不要求像素级还原
```

> **不要交付 Figma 链接就完事。**
> 我们需要能落地的：尺寸、间距、色值、字号的具体数值。
> 如果给的是图片标注，请确保数值清晰可读。

## 九、优先级（**如果时间不够，按这个顺序**）

```
P0  登录 → 桌台地图 → 开台 → 点单主界面 → 收银 → 支付结果
     ↑ 这六屏是 90% 的使用时长，做完这六屏系统就能用了

P1  挂单、退款、交接班、订单列表
     ↑ 每天都要用，但频率低

P2  商品管理、设置、报表
     ↑ 老板和店长用

P3  团购券、会员
     ↑ Wave 6 才做，可以先出概念
```

## 十、验收标准

我们会用以下标准判断设计是否通过：

```
□ 1366×768 下，主流程六屏信息完整、无需横向滚动
□ 收银员第一次用，不需要说明书就能完成开台→点菜→结账
□ 金额、桌号、数量这些数字一眼能读清、对齐
□ 8 种状态都有设计（特别是空状态和离线状态）
□ 密度符合收银台要求，不是"消费级 App"的留白风格
□ 组件规范完整，可以直接给开发实现
□ 不依赖鼠标悬停才能发现的功能
□ 对比美团收银：操作路径更短或持平
```
